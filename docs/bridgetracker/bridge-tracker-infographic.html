aggkit-proxy · bridge status tracker

One endpoint to follow a bridge
from bridgeAsset() to claimed

The tracker is a component of the aggkit proxy. Given the transaction that created a bridge — bridgeAsset() or bridgeMessage(), both are supervised — it aggregates data from the origin network, the Agglayer and the destination network, and answers a single question: where is my bridge right now?

8 lifecycle states 3 bridge routes REST + WebSocket full status on every update per-step error detail
01 · Lifecycle

The eight states of a bridge

Every bridge moves through a subset of these states, from the BridgeEvent emitted by bridgeAsset() or bridgeMessage() until it is claimed on the destination network. Where a bridge starts depends on where it was created: on L1 it waits for a GER update; on an L2 it waits for a LER update. The badge is the BridgeStep enum value returned by the API; the tags show which routes visit each state.

0
WaitingGERUpdate L1→L2

The bridge has been created on L1 — BridgeEvent emitted — but the Global Exit Root has not been updated yet (e.g. forceUpdateGlobalExitRoot=false).

1
WaitingLERUpdate L2→L1L2→L2

The bridge has been created on an L2 — BridgeEvent emitted — but the network's Local Exit Root has not been updated yet.

2
PendingInclusion L2→L1L2→L2

The LER is updated but the bridge is not yet part of any certificate. The Aggsender will pick it up when composing the next certificate.

3
CertificatePending L2→L1L2→L2

The bridge is included in a certificate that has been sent to the Agglayer and is awaiting progress.

4
CertificateProcessing L2→L1L2→L2

The certificate is walking the Agglayer states (Proven, Candidate…). An InError certificate surfaces right here as a step-level error — see ErrorStep — instead of moving the bridge elsewhere. The step loops on every certificate state change until settlement.

5
WaitingGERInjection L1→L2L2→L2

The GER that covers the bridge exists on L1, but the Aggoracle has not injected it into the destination L2 yet.

6
WaitingClaim L1→L2L2→L1L2→L2

The GER that includes the bridge is available on the destination network. The bridge is ready to be claimed with claimAsset() / claimMessage().

7
Claimed L1→L2L2→L1L2→L2

Terminal state — the asset has been claimed on the destination network and delivered to the recipient.

These values are the BridgeStep enum, carried in every all_steps[].step entry: 0→WaitingGERUpdate … 7→Claimed. The envelope doesn't repeat it at the top — instead it carries step_index (the position within all_steps of the step that explains the bridge's status), while tracking_status/tracking_status_string carry the lifecycle itself. Every enum field ships with a *_string companion, so clients never need a mapping table.

02 · Routes

Three routes, three different paths

Not every bridge visits every state. The direction decides where the bridge starts (WaitingGERUpdate on L1, WaitingLERUpdate on an L2), whether it needs a certificate (only bridges leaving an L2) and whether it needs a GER injection (only bridges arriving at an L2). Skipped states are shown crossed out; ⟳ marks the step that loops while the certificate changes state.

L1 → L2 no certificate — L1 is the source of truth
0 · WaitingGERUpdate→ 1–4 · certificate→ 5 · WaitingGERInjection→ 6 · WaitingClaim→ 7 · Claimed

GER update (L1→L2): the deposit updates the GER directly on L1, so it jumps straight to waiting for the Aggoracle to inject that GER into the destination L2. No certificate is involved.

L2 → L1 certificate, but no injection needed
1 · WaitingLERUpdate→ 2 · PendingInclusion→ 3 · CertificatePending→ 4 · CertProcessing ⟳→ 5 · injection→ 6 · WaitingClaim→ 7 · Claimed

Settled by Agglayer (L2→L1): the certificate walks the Agglayer states inside CertificateProcessing — a failed certificate (InError) surfaces there as a step-level error. Settlement happens on L1, which is also the destination: the GER is already there, so the bridge becomes claimable the moment it settles.

L2 → L2′ the full path — certificate and injection
1 · WaitingLERUpdate→ 2 · PendingInclusion→ 3 · CertificatePending→ 4 · CertProcessing ⟳→ 5 · WaitingGERInjection→ 6 · WaitingClaim→ 7 · Claimed

Settled by Agglayer (L2→L2): after settlement on L1, the Aggoracle still has to inject the new GER into the destination L2′ before the claim can happen. Two exit-root updates are involved — each reported in the result of its own step.

04 · REST API

    
Ask once, get the full picture

    

      One REST endpoint covers the whole tracker. You identify the bridge by the network where it was
      sent and the hash of the transaction that created it — nothing else.
    


    

      GET
      /tracker/v1/network/{network_id}/tx/{tx_hash}
    


    

      

        
ParamLocationTypeDescription

        
          
network_idpathuint32Network where the bridge transaction was sent (0 → Mainnet)

          
tx_hashpathHashHash of the transaction that created the bridge (bridgeAsset or bridgeMessage)

        
      

    


    

      

      

        
Calling is subscribing. The first call for a transaction adds the bridge to the tracker's
        list of supervised bridges. From then on the tracker keeps its status up to date on its own.

      

    


    

      

      

        
Always 200 — no 202, no 404. Every response is the same TrackingData
        shape; only its bridge_status/step_index/all_steps/error
        fields change — even when the tracker gives up on the tx entirely.

      

    


    

      

        bridge_status: null
        
Just registered, no info yet

        
The bridge was added to the supervised list but nothing is known about it yet:
        tracking_status is registered and
        bridge_status, step_index and
        all_steps are all null. Poll again until
        they're populated — or use the WebSocket and skip polling entirely.

      

      

        bridge_status: {…}
        
Status is known

        
The bridge is supervised and resolved: the same TrackingData now carries
        a populated bridge_status — the bridge's identity: type, and the block/log
        of the tx that created it — plus step_index and
        all_steps: the whole expected path with per-step progress and dates.

      

      

        error: {…}
        
The tracker gave up — no 404

        
The transaction never existed on the network, or existed but emitted no
        BridgeEvent (not a bridge transaction): after
        NotFoundAfter consecutive misses the tracker stops trying.
        tracking_status becomes error,
        bridge_status/step_index/all_steps
        stay null forever, and error carries
        why — see ErrorStep. Polling again keeps answering
        the same thing; there's nothing left to wait for.

      

    


    
Health check

    

      A second endpoint answers a different question: is this instance alive, and which build is it
      running? It takes no parameters and has no side effects — it does not register
      anything in the supervised list.
    


    

      GET
      /tracker/v1/health
    


    

      

        
FieldTypeDescription

        
          
statusstringAlways "ok" — the endpoint itself always returns 200 OK

          
instanceIdstringUUID generated at startup; changes on every execution. Two responses with different instanceId come from different instances (or the same one after a restart)

          
configSha1stringsha1 (hex) of the config file the instance was started with — lets you verify all instances run the same configuration

          
versionVersionInfoBuild info of the running binary: version, gitRev, gitBranch, buildDate, goVersion, os, arch

        
      

    


    

      

      

        
Useful behind a proxy. Beyond liveness/readiness probes, instanceId and
        configSha1 make it easy to detect the multi-instance pitfalls described in the
        deployment note below — mismatched configs, or requests bouncing between instances.

      

    

  


  

    
05 · WebSocket

    
Or subscribe, and let the tracker push

    

      The same path with a /ws suffix upgrades to a WebSocket. Connecting registers the
      bridge exactly like the REST call, but instead of polling, the client receives a message every time
      anything changes.
    


    

      GET
      /tracker/v1/network/{network_id}/tx/{tx_hash}/ws
    


    
Every frame is a JSON envelope — { "type": …, "data": … } — with two message types:


    

      

        status
        
The full TrackingData — never a delta. Sent immediately on connect, with
        bridge_status/step_index/all_steps all null if
        the tracker has no information yet, or all populated if it does. Pushed again on every change:
        tracking_status moves, bridge_status/step_index/all_steps
        fill in, step_index moves, a step in all_steps changes status or dates, the
        certificate status changes, or the tracker gives up resolving the bridge at all
        (error fills in instead).

      

      

        error
        
ErrorData with an HTTP-like code — 400 invalid path parameters only —
        then the server closes the connection. This is a pre-registration failure: once a bridge is
        registered, every outcome, including the tracker giving up on it, arrives as a status
        message instead.

      

    


    

      

      

        
Clean ending. The connection closes normally (code 1000) right
        after the final status message for either terminal outcome: the bridge
        reaches Claimed (tracking_status_string: "finished"),
        or the tracker gives up resolving it at all
        (tracking_status_string: "error" with bridge_status: null
        and error set). A step-level error on an otherwise-resolved bridge is
        not terminal — the connection stays open and the tracker keeps retrying. Keepalive is standard
        ping/pong — most WebSocket libraries handle it automatically.

      

    

  


  

    
06 · Response

    
Anatomy of a TrackingData response

    

      The same envelope everywhere — REST body and WebSocket status frames.
      tracking_status carries the bridge's entire lifecycle — registered,
      then running / error / finished once resolved — so none of bridge_status,
      step_index or all_steps need a status of their own: all three are
      null while tracking_status is registered, and from then on
      together they carry the full picture below — not just where the bridge is, but the whole path it is
      expected to walk, with timing per step.
    


    

      

        
tracking_status · bridge_status

        
tracking_status: 0→registered (no info yet,
        bridge_status: null), 1→running,
        2→error (a step reached an error), 3→finished
        (reached Claimed). One field replaces what used to be two.

      

      

        
bridge_type · bridge_leaf_type

        
What kind of bridge (L1→L2, L2→L1,
        L2→L2) and whether it carries an asset or a message
        (Asset / Message). Numeric enums with
        *_string companions.

      

      

        
block_number · log_index

        
Where the creating bridgeAsset()/bridgeMessage()
        call lives on the origin network: the block it was mined in and the position of its
        BridgeEvent log within that block — a stable pointer back to the
        on-chain event, handy for cross-referencing an explorer.

      

      

        
step_index

        
Points into all_steps at the step that explains the envelope's
        tracking_status: the step in progress when running,
        the step in error when error, or the last one
        (Claimed) when finished.

      

      

        
all_steps[]

        
The full expected path for this route. Each step carries a status
        (pending / inProgress / done / error), start and end dates, and an
        expected_duration — everything a UI needs to render a progress tracker.

      

      

        
result (per step)

        
Step outcomes live inside each step, not at the top level: the GER
        (WaitingGERUpdate) or LER (WaitingLERUpdate)
        produced with its block number, the certificate data — id, status, settlement tx —
        (CertificateProcessing), and the claim tx
        (WaitingClaim). null until the step completes,
        and for steps without a result.

      

      

        
all_steps[].error (per step)

        
Set only when a step's status is error (3).
        error_type tells you whether it's transient,
        permanent, or exhausted (retries given up on);
        retry_count and description[] carry how many
        attempts and why.

      

      

        
error (whole bridge)

        
null unless the tracker gave up trying to resolve the bridge at all —
        the tx doesn't exist, or isn't a bridge transaction. Same ErrorStep shape as
        above, but here retry_count counts not-found polls and
        error_type is always exhausted. When this is set,
        bridge_status/step_index/all_steps
        stay null forever — there's nothing to resolve.

      

    


    
Right after registering, the envelope looks like this:


    
{
  "tracking_status": 0, "tracking_status_string": "registered",
  "network_id": 5, "tx_hash": "0x9ac1e4…",
  "bridge_status": null,
  "step_index": null,
  "all_steps": null,
  "error": null
}

    
…until the tracker resolves the bridge. From then on every
    response keeps the same envelope, with tracking_status mirroring the bridge's
    lifecycle and bridge_status/step_index/all_steps
    filled in — here, a certificate has hit an error:


    
{
  "tracking_status": 2, "tracking_status_string": "error",
  "network_id": 5, "tx_hash": "0x9ac1e4…",
  "bridge_status": {
    "bridge_type": 2,  "bridge_type_string": "L2->L2",
    "bridge_leaf_type": 0, "bridge_leaf_type_string": "Asset",
    "block_number": 5012301, "log_index": 1
  },
  "step_index": 3,
  "all_steps": [
    { "step": 1, "step_string": "WaitingLERUpdate", "status": 2, "status_string": "done",
      "start_date": "2026-07-21T09:14:02Z", "end_date": "2026-07-21T09:14:31Z",
      "result": { "network_id": 3, "ler": "0x2c41…", "block_number": 5012345 } },
    { "step": 2, "step_string": "PendingInclusion", "status": 2, "status_string": "done" },
    { "step": 3, "step_string": "CertificatePending", "status": 2, "status_string": "done" },
    { "step": 4, "step_string": "CertificateProcessing", "status": 3, "status_string": "error",
      "expected_duration": "5m0s", "result": null,
      "error": { "error_type": 0, "error_type_string": "transient",
        "retry_count": 2,
        "description": ["agglayer grpc: context deadline exceeded"] } },
    … WaitingGERInjection, WaitingClaim, Claimed (pending) …
  ],
  "error": null
}


    

      

      

        
A step error stops the whole bridge — but not necessarily for long. The moment any step's
        status becomes error (3), the envelope's
        tracking_status flips to error too, and
        step_index points straight at it. What happens next depends on
        error_type:
        transient (0) means the tracker keeps retrying that step on its own —
        retry_count keeps climbing and description[] gains
        one entry per occurrence, and tracking_status returns to
        running once it clears. permanent (1) and
        exhausted (2) mean it won't resolve by itself. Note the top-level
        error field stays null throughout — it is reserved
        for a different, more final failure.

      

    


    
And if the tracker never manages to resolve the bridge at
    all — the tx doesn't exist, or isn't a bridge transaction — bridge_status,
    step_index and all_steps stay null
    forever, and error fills in instead:


    
{
  "tracking_status": 2, "tracking_status_string": "error",
  "network_id": 5, "tx_hash": "0x7b3f2a…",
  "bridge_status": null,
  "step_index": null,
  "all_steps": null,
  "error": { "error_type": 2, "error_type_string": "exhausted",
    "retry_count": 10,
    "description": ["transaction 0x7b3f2a… does not exist on network 5 or is not a bridge transaction"] }
}


    

      

      

        
Terminal — polling again won't help. This is the same ErrorStep
        shape as a per-step error, but here retry_count counts consecutive
        not-found polls (NotFoundAfter in the tracker's config) rather than step
        retries, and error_type is always exhausted — there
        is no transient/permanent distinction for a tx that
        was never found. The tracker stops tracking this tx_hash for good.

      

    


    

      

      

        
Deployment note — the server is stateful. The supervised-bridges list lives in the instance that
        served the request. Behind a load balancer with several instances, polls can see
        bridge_status flicker between null and populated,
        and WebSockets re-register on reconnect. Mitigations: a single instance,
        sticky sessions by tx_hash, or a shared store for the supervised list.
